# MVP 테스트 커버리지 가이드

## 한 줄 정의

**테스트 커버리지**는 테스트가 코드의 어느 부분을 실행했는지를 나타내는 측정값이다. 100% 커버리지가 목표가 아니라, 리스크가 높은 영역에 테스트가 집중됐는지가 품질에서 더 큰 차이를 만든다. 커버리지 수치 자체가 결함 없음을 증명하지는 않는다.

## 테스트 레벨 4단계

- **단위 테스트(unit)** — 함수·모듈 하나를 독립적으로 검증.
- **통합 테스트(integration)** — 여러 모듈이 이어지는 구간을 검증.
- **시스템 테스트(system)** — 전체 시스템이 명세대로 동작하는지 검증.
- **인수 테스트(acceptance)** — 사용자 관점의 시나리오가 끝까지 동작하는지 검증.

## 팀 규모별 권장 목표

- **1명** — 단위 테스트 핵심 5~10개 + 수동 통합 테스트 체크리스트. 자동화는 핵심 도메인 함수(인증·결제·계산 등)만. 통합 자동화·E2E·변형 테스트는 생략 가능하지만, 핵심 기능 동작 확인용 수동 테스트 체크리스트는 절대 생략 금지다.
- **2~3명** — 핵심 경로 라인 커버리지 **30~50%** 목표. 자동화 우선순위는 단위 테스트 + 핵심 API 1~2개 통합 테스트. 분기 커버리지·변형 테스트·E2E 자동화는 생략 가능하지만, CI에서 자동 단위 테스트 실행은 절대 생략 금지다.
- **4~6명** — 핵심 경로 라인 커버리지 **50~70%** 목표. 자동화 우선순위는 단위(주력) + 통합(주요 API 5~10개) + 핵심 사용자 시나리오 인수 테스트 2~3개. 모든 분기 커버·시각적 회귀·부하 테스트는 생략 가능하지만, 인수 테스트 최소 3개는 꼭 만든다.
- **7~10명** — 라인 커버리지 **70% 이상** + 분기 커버리지 50% 이상까지 가능. 자동화 우선순위는 단위 + 통합 + 시스템 + E2E(주요 시나리오 5~8개). 테스트 담당자 1~2명 지정 가능. PR 머지 차단 기준(커버리지 하락 시 빨간불)은 절대 생략 금지다.

## 어디에 테스트를 쓸 것인가

- **가치 있는 곳** — 비즈니스 로직, 계산, 검증, 예외 처리, 상태 전이.
- **가치 적은 곳** — 1줄짜리 getter/setter, 단순 위임 함수, 프레임워크가 이미 보장하는 영역.

사용자 시나리오(회원가입 → 주문 → 결제) 기반으로 "이 경로는 반드시 동작해야 한다"를 먼저 정하고, 그 경로에 닿는 함수부터 테스트를 쌓는다.

## 흔한 실수

- **100% 커버리지를 목표로** — 모든 함수에 테스트를 다 쓰느라 핵심 기능 개발이 밀리는 패턴이다. 100%는 잘못된 안도감을 주고, 정작 리스크 높은 영역의 테스트 품질은 보장하지 않는다. 사용자 시나리오 핵심 경로 위주 50~70%를 목표로 잡는 게 현실적이다.
  - bad: 커버리지 100%를 목표로 잡아 핵심 개발이 밀렸다.
  - good: 핵심 경로 위주 60% 커버리지를 목표로 잡았다.
- **모든 함수를 테스트** — 1줄짜리 getter/setter에도 테스트를 쓰면 코드 변경 시 갱신 부담만 생기고 결함 발견 능력은 0에 가깝다. 비즈니스 로직·계산·검증·예외 처리가 들어간 함수 위주로 쓴다.
  - bad: 1줄짜리 getter/setter에도 테스트를 모두 작성했다.
  - good: 로직·계산·검증이 들어간 함수만 골라 테스트했다.
- **인수 테스트 누락** — 단위 테스트만 다 통과해도 시스템 차원에서 안 도는 경우가 흔하다. 주요 사용자 흐름 1~3개를 통합 또는 E2E로 검증해야 진짜 동작 보증이 된다.
  - bad: 단위 테스트만 있고 전체 흐름은 검증하지 않았다.
  - good: 회원가입부터 결제까지 시나리오 테스트를 만들었다.

## 핵심 요약

**핵심 경로 우선, 100%는 함정이다.** 사용자 시나리오를 기준으로 리스크 높은 영역에 테스트를 집중하고, 커버리지 수치는 참고 지표로만 쓴다.
