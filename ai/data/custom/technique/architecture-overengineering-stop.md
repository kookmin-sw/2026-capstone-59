# 아키텍처 과잉설계 회피

## 한 줄 정의

**아키텍처 과잉설계**는 현재 필요보다 훨씬 복잡한 구조를 미리 도입해, 즉각적인 가치 없이 복잡도와 운영 비용만 누적시키는 현상이다. 소규모 팀에서 가장 흔한 실패 원인 중 하나다.

## 왜 소규모 팀에서 특히 위험한가

아키텍처 결정은 시스템의 일생에 영향을 미치는 제약을 만든다. 복잡한 구조를 미리 깔면 학습·운영·디버깅 비용이 전부 동시에 붙고, 제한된 프로젝트 기간 안에 정작 핵심 기능을 완성할 시간이 사라진다. 가장 단순한 스타일로 시작해 필요가 명확해졌을 때 쪼개는 게 원칙이다.

## 팀 규모별 권장 스타일

- **1명** — 단일 모놀리식 앱 1개 + 단일 DB가 정답. 추천 스택은 FastAPI/Express/Spring Boot 단일 앱 + PostgreSQL 또는 SQLite. 마이크로서비스·쿠버네티스(K8s)·메시지 큐·이벤트 소싱은 절대 도입하지 않는다. 컷오프는 "동작하는 한 페이지"가 우선이며, 분리는 동작한 뒤에 고려한다.
- **2~3명** — 단순 3계층(프론트 / 백엔드 / DB) 구조에 단일 DB로 충분하다. 캐시(Redis)는 명확한 성능 병목이 눈에 보일 때만 도입한다. 마이크로서비스·K8s·GraphQL Federation·CQRS는 도입 금지. 컴포넌트를 3~5개 이상으로 쪼개고 싶어지면 "정말 필요한가"를 한 번 더 묻는다.
- **4~6명** — 3계층 구조로 충분하고, 분리가 필요하면 모놀리식 안에서 도메인별 모듈을 나눈다. 캐시·CDN·단순 큐는 필요할 때만 추가. 마이크로서비스·K8s 풀세트·이벤트 소싱은 도입 금지다. 서비스를 3개 이상으로 쪼개려는 충동이 들면 멈춰서 이유를 검증한다.
- **7~10명** — 모놀리식 + 도메인 경계를 명확히 잡고, **팀 분할이 분명한 경우에만** 일부를 서비스로 분리한다(서비스는 3개 이하 권장). API 게이트웨이·모니터링·로깅 분리·IaC(Terraform 등)는 규모가 올라가면 가치가 있다. K8s 풀세트(EKS/GKE)·이벤트 소싱·CQRS 전체 적용은 여전히 도입 금지다.

## 흔한 실수

- **트렌드 따라가기** — "요즘 다들 마이크로서비스 쓴다"는 이유로 5개 서비스로 쪼개는 패턴이다. MSA는 운영 비용과 복잡도가 폭발하며, 소규모 팀의 제한된 기간 안에 운영 학습 자체가 불가능하다. 팀이 다룰 수 있는 범위에서 모놀리식으로 시작하고, 명확한 분리 이유가 생긴 뒤에 쪼갠다.
  - bad: 요즘 다들 MSA 쓴다고 해서 5개 서비스로 쪼갰다.
  - good: 모놀리식으로 시작하고 분리 이유가 생긴 뒤에 쪼갰다.
- **미래 확장을 미리 준비** — 100만 사용자를 대비해 K8s + 메시지 큐 + 캐시 클러스터를 미리 까는 경우. 실제론 1만 사용자도 안 오는 상황에서 비용만 치른다. 단일 서버로 시작하고 트래픽이 보이면 그때 확장한다.
  - bad: 100만 사용자를 대비해 K8s 클러스터를 미리 깔았다.
  - good: 단일 서버로 시작하고 트래픽이 보일 때 확장했다.
- **익숙하지 않은 기술 다 끌어쓰기** — 팀 누구도 안 써본 Kafka·gRPC·Rust를 한 번에 도입하면 학습 곡선이 프로젝트 기간 안에 안 들어온다. 팀에 1명 이상 경험이 있는 기술 위주로 선택하는 게 안전하다.
  - bad: 아무도 안 써본 Kafka·gRPC를 한 번에 도입했다.
  - good: 팀원 중 한 명이라도 경험 있는 기술을 골라 썼다.

## 핵심 요약

**동작 먼저, 분리는 나중.** 가장 단순한 스타일로 시작하고, 분리 이유가 말로 설명될 때만 쪼갠다. 트렌드가 아니라 팀의 현재 역량이 선택 기준이다.
