# 동료 리뷰(Peer Review) vs 인스펙션(Inspection)

## 한 줄 정의

- **동료 리뷰** — 동료 1~2명이 코드를 읽고 의견을 남기는 가벼운 정적 검토. PR 리뷰가 대표 형태다.
- **인스펙션** — 가장 형식적인 정적 검토. 저자·중재자·낭독자·기록자 역할을 나누고 체크리스트·회의록까지 남기는 무거운 방식이다.

결함은 일찍 발견할수록 고치는 비용이 작다. 코드를 실행하지 않고 사람이 읽으며 결함을 찾는 이 두 방식은 단위 테스트만큼 중요한 결함 발견 활동이다.

## 형식의 4단계

형식이 가벼운 순서로 다음 네 단계가 있다.

- **워크스루(walkthrough)** — 작성자가 다른 사람에게 코드를 설명하며 흐름을 함께 따라가는 비공식 검토.
- **동료 리뷰(peer review)** — 동료 1~2명이 코드를 읽고 의견을 남김. PR 리뷰가 이에 해당.
- **기술 검토(technical review)** — 정해진 절차에 따라 팀 일부가 모여 결함을 식별.
- **인스펙션(inspection)** — 역할 분담, 체크리스트, 회의록까지 갖춘 가장 형식적인 방식.

## 팀 규모별 운영 형태

- **1명** — 자체 리뷰로 동료 리뷰를 흉내 낸다. 작성 후 24시간 뒤 자기 PR을 본인이 한 번 더 읽기. 인스펙션이나 정식 동료 리뷰는 생략 가능하지만, 작성 직후 바로 머지하는 습관은 절대 피한다. 최소 한 번은 다시 보기가 규칙.
- **2~3명** — 페어 리뷰로 간다. PR에 1명 승인 필수, 짝을 바꿔가며 리뷰한다. 24시간 내 리뷰 응답 규칙을 두면 흐름이 끊기지 않는다. main에 직접 commit하지 않고 PR 형식을 도입하는 것은 절대 생략 금지다.
- **4~6명** — PR 리뷰(1~2명 승인 필수)가 기본이다. 리뷰 응답 24~48시간, 가벼운 리뷰 체크리스트를 둔다. 핵심 모듈에는 프로젝트 기간 중 2~4회 인스펙션을 추가하면 좋다. PR 머지 전 최소 1명 승인 + CI 통과는 절대 생략 금지다.
- **7~10명** — PR 리뷰(2명 승인) + 핵심 모듈 인스펙션. 24시간 응답 SLA, 정식 체크리스트, 리뷰어 자동 할당, 모듈 소유자(code owner) 지정까지 간다. 리뷰 품질 자체를 정기 점검해 형식적 승인을 방지한다.

## 흔한 실수

- **형식적 LGTM** — PR이 올라오면 30초 만에 "LGTM"만 누르는 패턴이다. 형식적 승인은 리뷰 효과를 0으로 만들고 결함이 그대로 머지된다. 최소 핵심 변경 부분은 읽고, 한 가지 이상 질문 또는 제안을 남기도록 팀이 합의한다.
  - bad: PR이 올라오자마자 30초 만에 LGTM을 눌렀다.
  - good: 핵심 변경 부분을 읽고 질문 한 줄을 남기고 승인했다.
- **너무 큰 PR** — 1000줄 PR을 한 번에 올리면 리뷰어가 끝까지 안 읽는다. 200~400줄 단위로 나눠 올리면 리뷰 품질이 유지된다.
  - bad: 한 PR에 1000줄을 통째로 올려버렸다.
  - good: 기능 단위로 쪼개 300줄짜리 PR로 올렸다.
- **리뷰 응답 지연** — PR이 일주일 방치되면 작업 흐름이 끊기고 컨텍스트도 휘발된다. 24~48시간 응답 SLA를 팀이 합의해야 리뷰 자체가 프로세스로 자리잡는다.
  - bad: PR이 일주일 동안 리뷰 없이 방치됐다.
  - good: 24시간 내 한 줄 의견을 남기기로 팀이 합의했다.

## 핵심 요약

4~6명 구간 디폴트는 **PR 기반 동료 리뷰**다. 인스펙션은 핵심 모듈에만 프로젝트 기간 중 2~4회. 리뷰 효과는 형식이 아닌 "읽고 질문 한 줄"에서 나온다.
