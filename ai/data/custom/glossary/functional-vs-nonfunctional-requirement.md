# 기능 요구사항(FR) vs 비기능 요구사항(NFR)

## 한 줄 정의

- **기능 요구사항(FR)** — 시스템이 **무엇을** 해야 하는지 정의한다. 입력·출력·동작 조건이 분명할수록 좋은 문장이 된다.
- **비기능 요구사항(NFR)** — 시스템이 그 기능을 **얼마나 잘** 해야 하는지 정의한다. 성능·보안·사용성 같은 품질 속성이다.

## 왜 따로 다뤄야 하는가

FR만 잔뜩 적어두고 NFR을 빼면 설계·아키텍처 결정에 기준이 사라진다. 반대로 정량 수치가 빠진 NFR("빠르게 응답해야 한다")은 검증이 불가능해 사실상 없는 것과 같다. 따라서 FR은 기능 단위로, NFR은 정량 측정 가능하게 따로 관리한다.

## 팀 규모별 권장 분량

- **1명** — FR 5~10개, NFR 1~2개(성능·보안 정도). NFR은 "응답 2초 이내"처럼 한 줄 정량화한다. 호환성·이식성·유지보수성 NFR은 생략 가능하지만, 개인정보를 다루면 보안 NFR은 절대 생략 금지다.
- **2~3명** — FR 10~15개, NFR 2~3개(성능·보안·사용성). NFR마다 측정 방법 한 줄을 덧붙인다. 성능 NFR은 정량 수치 포함이 필수다.
- **4~6명** — FR 15~25개, NFR 3~5개. 9개 NFR 카테고리 중 프로젝트에 해당하는 5개 정도만 깊이 있게 작성한다. 추천: 성능·보안·사용성·신뢰성·제약(법규). 정량 측정 가능한 NFR 작성은 외부 보고용 자료의 핵심 포인트다.
- **7~10명** — FR 25~40개, NFR 5~7개. FR은 에픽·기능·스토리 3계층으로 분해하고, NFR에는 검증 방법과 인수 기준을 함께 명시한다. NFR 변경 시 영향 분석 절차를 두는 것이 좋다.

## NFR 정량화 예시

- **성능** — bad: "응답이 빨라야 한다." / good: "주요 API 응답이 2초 이내여야 한다(동시 사용자 20명 가정)."
- **가용성** — bad: "서비스가 안정적이어야 한다." / good: "월 99% 이상 가용, 연속 다운타임은 10분 이내로 유지한다."
- **사용성** — bad: "사용하기 쉬워야 한다." / good: "신규 사용자가 회원가입부터 첫 게시글 작성까지 3분 안에 완료한다."

## 흔한 실수

- **NFR을 통째로 빠뜨리기** — FR 목록만 잔뜩 쓰고 NFR 섹션 자체가 없는 경우다. NFR 없는 명세는 설계 단계에서 품질 기준이 사라진다. FR 옆에 별도 섹션으로라도 "응답 2초 이내, 99% 가용성, HTTPS 필수"를 두는 게 좋다.
  - bad: 기능만 잔뜩 적고 비기능 요구사항은 따로 적지 않았다.
  - good: 기능 목록 옆에 응답 시간·가용성 기준을 따로 적어뒀다.
- **정량화 없는 NFR** — "빠르게 응답한다"는 측정 불가능해 검증이 안 된다. "API 응답 2초 이내(동시 사용자 20명 가정)"처럼 수치와 조건을 함께 적는다.
  - bad: 시스템이 빠르게 응답해야 한다.
  - good: 동시 20명 기준 API 응답 2초 이내를 명시했다.
- **모든 NFR 카테고리를 형식적으로 채우기** — 9개 카테고리에 한 줄씩 기계적으로 채우면 검토 비용만 늘고 가치는 안 준다. 프로젝트 컨텍스트에 해당하는 3~5개만 깊이 있게 작성한다.
  - bad: 성능·보안·호환성 등 9개 항목에 한 줄씩 다 채웠다.
  - good: 성능·보안·사용성 3개만 골라 측정 방법까지 적었다.

## 핵심 요약

FR은 "무엇을", NFR은 "얼마나 잘". NFR은 카테고리를 몇 개 고르되 모두 정량 측정 가능한 문장으로 적는다.
