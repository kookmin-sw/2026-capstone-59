# 설계 결정 근거 (Design Rationale, ADR)

## 한 줄 정의

**설계 결정 근거**는 "무엇을 선택했는가"뿐 아니라 "왜 그렇게 결정했는가·어떤 대안을 검토했는가"를 함께 남기는 활동이다. 대표 형식은 **ADR(Architecture Decision Record, 아키텍처 결정 기록)**이며, 결정 하나당 1~2페이지짜리 마크다운 파일 한 개를 만드는 것이 일반적이다.

## 왜 결정 근거를 남겨야 하는가

결정의 근거가 없으면 3개월 뒤 누구도 의도를 알 수 없고, 변경이 필요할 때 무엇을 고려해야 하는지 처음부터 다시 분석해야 한다. 신입 합류자도 "왜 이 기술을 썼는지" 물을 때 답할 사람이 없다. 결정 당시의 컨텍스트·대안·트레이드오프가 박혀 있어야 후속 변경 검토가 가능하다.

## ADR 6항목

- **결정(decision)** — 무엇을 선택했는가.
- **컨텍스트(context)** — 어떤 상황·제약에서 결정했는가.
- **검토한 대안(alternatives considered)** — 다른 후보는 무엇이었나.
- **근거(rationale)** — 왜 이 대안을 골랐나. 장단점 비교.
- **결과(consequences)** — 이 결정이 가져올 영향·트레이드오프.
- **상태(status)** — 제안됨 / 승인됨 / 폐기됨.

## 팀 규모별 형태

- **1명** — README 또는 GitHub Wiki에 "결정 1줄 + 이유 1줄" 메모로 충분하다. 정식 ADR 폴더와 상태 관리는 생략 가능하지만, 핵심 결정 3~5개에 대한 한 줄 이유 메모는 절대 생략 금지다. 3개월 뒤 본인이 봐도 이해될 수준이면 된다.
- **2~3명** — 간단 ADR을 쓴다. 1페이지 · 5섹션 구조로 핵심 결정 5~10개. 도구는 `docs/decisions/` 폴더에 마크다운 파일들. 상태 워크플로와 자동 인덱스는 생략 가능하지만, 대안 비교(최소 2개 후보 + 선택 이유)는 꼭 남긴다.
- **4~6명** — 정식 ADR로 간다. 1~2페이지 · 6섹션 전부 채우기. 핵심 결정 10~15개(스택·아키텍처·DB·인증 등) 수준. 도구는 `docs/adr/` 폴더 + adr-tools 또는 단순 마크다운. **결정한 그날 또는 다음 회의 전까지 작성**이 원칙이며 사후 몰아쓰기는 금지다.
- **7~10명** — 정식 ADR + 결정 회의 회의록 링크까지 이어둔다. 결정 영향 평가와 책임자를 함께 남기고, ADR 리뷰어를 1명 이상 지정해 승인 표시를 단다. Notion DB 또는 Confluence로 인덱스를 운영한다.

## 흔한 실수

- **결정만 적고 대안 비교 누락** — "DB는 PostgreSQL로 결정" 한 줄만 남기면 후속 변경 검토가 불가능하다. "후보는 MySQL/MongoDB였고, PostgreSQL은 JSON 타입과 팀원 1명의 운영 경험 덕분에 선택"처럼 대안·근거까지 붙여야 ADR이 된다.
  - bad: DB는 PostgreSQL로 결정했다.
  - good: 후보 3개를 비교한 뒤 운영 경험 있는 PostgreSQL을 골랐다.
- **사후에 한꺼번에 작성** — 프로젝트 후반에 ADR 10개를 몰아쓰면 결정 당시의 컨텍스트가 휘발돼 진짜 이유가 왜곡된다. 결정한 그날 또는 다음 회의 전까지 한 편씩 작성하는 규칙을 둔다.
  - bad: 프로젝트 후반에 ADR 10개를 한꺼번에 몰아 썼다.
  - good: 결정한 당일 ADR 한 편을 바로 작성했다.
- **모든 결정에 ADR 작성** — 버튼 색깔까지 ADR로 쓰면 작성 부담이 커져 정작 중요한 결정에 ADR을 안 쓰게 된다. 되돌리기 어려운 결정(스택·아키텍처·핵심 라이브러리 등)에만 ADR을 적용한다.
  - bad: 버튼 색깔 결정에도 정식 ADR을 작성했다.
  - good: 되돌리기 어려운 스택·아키텍처 결정에만 ADR을 썼다.

## 핵심 요약

ADR은 "결정의 컨텍스트를 3개월 뒤에도 다시 읽을 수 있게 박제하는 장치"다. 되돌리기 어려운 결정에만 6항목을 결정 당일에 남기는 게 실용적이다.
