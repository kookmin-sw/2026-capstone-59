# 요구사항 추적 매트릭스 (Requirements Traceability Matrix, RTM)

## 한 줄 정의

요구사항 하나하나가 **어디에서 왔고**(출처·이해관계자) **어디로 이어지는지**(설계·코드·테스트)를 한 표에 정리해, 변경이 생겼을 때 영향 범위를 바로 파악할 수 있게 만든 장치다. 한국어로 풀면 "요구사항–기능–테스트 연결 표"에 가깝다. "매트릭스"라는 단어가 생소해 회피되기 쉽지만 개념 자체는 단순한 표다.

## 왜 필요한가

요구사항 하나를 바꾸면 설계·코드·테스트 몇 군데가 함께 바뀌어야 하는지 알아야 일정·품질이 안 무너진다. 매트릭스 없이 진행하면 프로젝트 중반에 "이 기능을 뺍시다"가 나올 때 영향 범위를 감으로 찍게 되고, 빠뜨린 부분이 데모에서 터진다. 양방향 추적(역방향: 요구사항 → 출처 / 전방: 요구사항 → 테스트)이 갖춰지면 변경 영향 분석이 수분 안에 끝난다.

## 팀 규모별 형태

- **1명** — 정식 매트릭스는 만들지 않는다. README 또는 메모에 "FR-1 = 회원가입 = signup.py" 식 한 줄 매핑만 남긴다. 핵심 기능 5개 정도의 요구사항 ↔ 코드 매핑 메모는 절대 생략 금지다. 도구는 텍스트 파일이나 마크다운으로 충분하다.
- **2~3명** — 간단 표로 시작한다. 컬럼은 요구사항 ID, 기능명, 담당자 정도. 도구는 Google Sheets 또는 Notion 페이지 한 장. 테스트 매핑과 정식 변경 이력은 생략 가능하지만, 요구사항에 ID(FR-1, NFR-1 등)를 부여하는 것은 꼭 해야 한다.
- **4~6명** — 정식 매트릭스를 쓴다. 컬럼은 요구사항 ID, 기능, 테스트 케이스, 상태 4개면 충분하다. 도구는 Google Sheets 또는 Notion 데이터베이스. 중간 마일스톤·최종 마일스톤 전 매트릭스 갱신은 외부 보고용 자료로도 활용되므로 절대 생략 금지다.
- **7~10명** — Jira 같은 이슈 도구의 링크 기반 추적으로 간다. Epic–Story–Task 계층 위에 테스트 케이스 ID까지 자동 연결되게 구성한다. 변경 이력과 책임자 표기는 꼭 남긴다.

## 도구 선택 가이드

| 팀 규모 | 추천 도구 | 비고 |
|---|---|---|
| 1명 | 텍스트 파일 / README | 매트릭스 아닌 한 줄 메모로 충분 |
| 2~3명 | Google Sheets, Notion 페이지 | 컬럼 3~4개 |
| 4~6명 | Google Sheets, Notion DB | 컬럼 4~5개 |
| 7~10명 | Jira(링크 기반) 또는 Confluence + Notion DB | 자동 연결 활용 |

## 흔한 실수

- **너무 일찍 정식 매트릭스 만들기** — 프로젝트 첫 주에 Excel로 30컬럼짜리를 만들면 요구사항이 계속 바뀌는 초반에는 갱신 부담만 크다. 요구사항 도출이 어느 정도 안정되는 Stage 3 후반에 시작하는 게 실용적이다.
  - bad: 프로젝트 첫 주에 30컬럼 매트릭스를 만들었다.
  - good: 요구사항이 안정된 3주차에 4컬럼 매트릭스로 시작했다.
- **만들어두고 갱신 안 하기** — 초기에 한 번 만들고 프로젝트 후반까지 방치하면 거짓 정보가 되고 실제 의사결정에 쓸 수 없다. 스프린트 회고마다 5분이라도 상태 컬럼만 갱신한다.
  - bad: 초기에 한 번 만들고 프로젝트 후반까지 안 봤다.
  - good: 스프린트 회고마다 상태 컬럼만이라도 5분 갱신했다.
- **컬럼을 너무 많이 만들기** — 우선순위·담당자·일정·코드 위치·리뷰어·비고를 모두 넣으면 갱신 부담이 기하급수로 커진다. 4~5컬럼(ID, 기능, 테스트, 상태)으로 시작하고 필요할 때만 추가한다.
  - bad: 10컬럼 매트릭스에 모든 정보를 다 채우려 했다.
  - good: 4컬럼으로 시작해 필요할 때만 컬럼을 추가했다.

## 핵심 요약

매트릭스는 "변경 영향을 수분 안에 파악하는 장치"다. 4~5컬럼에서 시작해 살아있게 유지하는 게 화려한 30컬럼 표보다 낫다.
